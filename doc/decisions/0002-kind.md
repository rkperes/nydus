# 0002 — kind over minikube, k3s, k3d

**Status:** Accepted · 2026-09-19

## Context

A multi-node Kubernetes cluster is needed on a single host, cheap to create and destroy
so that measurement runs start from a known state.

## Decision

[kind](https://kind.sigs.k8s.io) — one control plane, two workers.

Two workers rather than one: a single worker makes pod topology spread, disruption
budgets, and `kubectl drain` meaningless.

## Consequences

**Good**

- Multi-node from a few lines of config.
- Each node is a container, so node-level pressure can be induced directly —
  `docker update --memory` provokes eviction without special tooling.
- kubeadm-based, so it is upstream Kubernetes rather than a trimmed distribution.
  Component behaviour matches what the documentation describes.
- Create and destroy in a couple of minutes, which makes per-run clean state practical.

**Bad**

- No `LoadBalancer`. Needs MetalLB or `cloud-provider-kind` if it ever matters.
- Storage is `local-path-provisioner`. IO measurements from it are not representative.
- Inter-node latency is effectively loopback, so anything network-topology-sensitive is
  unmeasurable without `tc netem`.
- The cluster does not reliably survive a host reboot. Accepted for now; recovery is
  manual via `make cluster-up`.

These gaps are listed in [`doc/local/README.md`](../local/README.md) so they are
engineered around deliberately rather than discovered late.

## Alternatives considered

**k3s.** Real processes on real hosts, closer to production. Heavier to reset between
runs, and it trims or replaces components (Traefik, ServiceLB, its own storage backend)
whose behaviour is part of what is being studied.

**k3d.** k3s in Docker. Inherits the same substitutions.

**minikube.** Multi-node support is less central to its design, and the driver layer
adds a variable that does not need to exist.
